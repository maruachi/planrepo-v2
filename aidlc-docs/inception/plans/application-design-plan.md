# PlanRepo Application Design 계획

## 범위와 실행 근거

승인된 [실행 계획](execution-plan.md)과 2026-09-08의 “다음단계로 진행해줘.” 요청에 따라 최소 Application Design을 수행한다. 단일 로컬 앱 안의 논리 구성 요소를 정의하며 기술 스택, SQL 스키마 및 상세 파싱 알고리즘은 후속 단계에서 결정한다.

## 실행 체크리스트

- [x] 1. 요구사항, 스토리, 실행 계획과 기존 답변의 일관성을 확인한다.
- [x] 2. 설계 질문의 필요성을 평가하고 기존 결정으로 확정 가능한 범위를 기록한다.
- [x] 3. `components.md`에 구성 요소의 목적, 책임, 인터페이스를 정의한다.
- [x] 4. `component-methods.md`에 각 구성 요소의 메서드와 입출력 계약을 정의한다.
- [x] 5. `services.md`에 서비스 책임과 흐름별 조정 방식을 정의한다.
- [x] 6. `component-dependency.md`에 의존성 표, 통신 방식, 데이터 흐름도를 작성한다.
- [x] 7. `application-design.md`에 설계를 통합하고 후속 결정 사항을 명시한다.
- [x] 8. FR-1~FR-6 및 US-01~US-05 추적성, 인터페이스 일치, 범위·확장 준수와 문서 구문을 검증한다.
- [x] 9. 상태 및 감사 기록을 갱신하고 산출물 승인을 요청한다.

승인 근거: 2026-09-08 사용자의 “aidlc-docs/aidlc-state.md를 확인하고, 첫 번째 미완료 항목부터 이어서 진행해주세요.” 요청을 직전 설계 검토에 대한 승인 및 다음 단계 진행 지시로 기록했다.

## 질문 필요성 평가

| 범주 | 적용할 결정과 근거 | 추가 질문 |
| --- | --- | --- |
| 구성 요소 | 승인된 단일 앱 안에 UI, 조정 서비스, GitHub 읽기, 파싱, 렌더링, SQLite 저장, 내보내기 책임을 구분 | 없음: 실행 계획의 범위 구체화 |
| 메서드 | 연결, 조회, 질문 추출, 일괄 저장, 다운로드의 입출력 명시 | 없음: FR-1~FR-6에 필요한 내부 계약 |
| 서비스 | 사용자 흐름을 조정하는 하나의 애플리케이션 서비스 | 없음: 1.5일 단일 단위 결정 유지 |
| 의존성·통신 | 브라우저와 로컬 앱, 앱 내부 호출, GitHub 읽기 및 로컬 SQLite 접근 | 없음: 배포·다중 서비스 제외로 범위 확정 |
| 설계 패턴 | 단일 프로세스의 모듈화, 입력/출력 경계 분리 | 없음: 별도 패턴·프레임워크 강제 없음 |

사용자 선택이 필요한 새로운 제품 범위의 모호성은 발견하지 않았다. 질문을 만들기 위해 이미 승인된 결정을 다시 묻지 않는다. 질문 식별·원문 변경 처리의 상세 규칙은 예정된 Functional Design으로, 기술 스택은 NFR Requirements로 넘긴다. 이 판단은 사용자가 미작성 질문에 답하거나 새 산출물을 승인했다고 간주하지 않는다.
