# PlanRepo MVP 요구사항

## 의도 분석

- **사용자 요청**: Spec-Driven Development 및 AI-DLC 문서를 공유하고, 문서에서 미결정 질문을 추출하여 빠르게 합의할 수 있는 PlanRepo MVP 구축
- **요청 유형**: 신규 프로젝트
- **범위 추정**: 단일 로컬 웹 애플리케이션의 핵심 사용자 흐름
- **복잡도 추정**: 단순 MVP
- **요구사항 깊이**: 최소
- **완료 제한**: 1.5일

## 목표

공개 GitHub 저장소의 Markdown 명세 문서를 로컬 웹 화면에서 탐색하고, AI-DLC 형식의 미결정 질문을 한곳에 모아 답변한 뒤 결과를 로컬에 저장하고 수정된 Markdown으로 내보낼 수 있게 한다.

## 대상 사용자

- AI-DLC 또는 Spec-Driven Development 문서를 검토하는 개발자
- 프로젝트 문서의 미결정 사항을 정리하는 팀 구성원

## 핵심 사용자 흐름

1. 사용자가 공개 GitHub 저장소 URL과 Markdown 문서 폴더 경로를 입력한다.
2. 시스템이 해당 폴더의 Markdown 파일 목록을 불러온다.
3. 사용자가 문서를 선택해 렌더링된 내용을 본다.
4. 시스템이 문서에서 미결정 질문과 선택지를 추출해 대기열에 표시한다.
5. 사용자가 하나 이상의 질문에 답변을 선택한다.
6. 시스템이 답변을 SQLite에 저장하고, 선택 결과가 반영된 Markdown을 내려받을 수 있게 한다.

## 기능 요구사항

### FR-1 공개 GitHub 저장소 연결

- 사용자는 `github.com` 공개 저장소 URL을 입력할 수 있어야 한다.
- 사용자는 저장소 내부의 명세 문서 폴더 경로를 지정할 수 있어야 한다.
- 시스템은 인증 없이 접근 가능한 공개 저장소만 읽어야 한다.
- 저장소, 브랜치 또는 폴더를 읽을 수 없으면 원인을 이해할 수 있는 오류를 표시해야 한다.

### FR-2 Markdown 문서 탐색

- 시스템은 지정된 폴더 아래의 `.md` 파일 목록을 표시해야 한다.
- 사용자는 목록에서 문서를 선택할 수 있어야 한다.
- 시스템은 선택한 Markdown을 읽기 가능한 HTML로 렌더링해야 한다.
- 렌더링 시 위험한 HTML 또는 스크립트를 실행하지 않아야 한다.

### FR-3 의사결정 사항 추출

- 시스템은 다음 기본 AI-DLC 형식을 지원해야 한다.
  - 질문 제목: `## Question <번호>`
  - 선택지: `A)`, `B)`, `C)`와 같은 문자 선택지
  - 답변 위치: `[Answer]:`
- `[Answer]:`가 비어 있는 질문은 미결정 상태로 분류해야 한다.
- `[Answer]:`에 값이 있는 질문은 결정 완료 상태로 분류해야 한다.
- 형식이 잘못된 영역 때문에 전체 문서 처리가 실패해서는 안 되며, 해당 영역을 건너뛰거나 파싱 경고를 표시해야 한다.

### FR-4 미결정 사항 대기열

- 시스템은 모든 문서에서 추출된 미결정 질문을 하나의 목록에 표시해야 한다.
- 각 항목은 원본 문서, 질문 문구 및 선택지를 보여줘야 한다.
- 사용자는 대기열 항목에서 답변 하나를 선택할 수 있어야 한다.
- 답변된 항목은 대기열에서 제거되거나 완료 상태로 표시되어야 한다.

### FR-5 답변 저장 및 일괄 반영

- 선택한 답변은 SQLite에 저장되어 애플리케이션 재시작 후에도 유지되어야 한다.
- 사용자는 여러 질문의 선택 결과를 한 번에 확정할 수 있어야 한다.
- 시스템은 원격 GitHub 저장소를 수정하지 않아야 한다.
- 시스템은 확정 답변을 해당 `[Answer]:` 위치에 반영한 Markdown 파일을 내려받을 수 있게 해야 한다.

### FR-6 최소 상태 관리

- 시스템은 최근 연결한 저장소 URL과 문서 폴더 경로를 SQLite에 저장해야 한다.
- 문서별로 질문 식별자, 선택 답변 및 결정 시각을 저장해야 한다.
- 동일 문서를 다시 불러왔을 때 저장된 답변을 연결할 수 있어야 한다.

## 오류 처리

- 올바르지 않은 GitHub URL은 네트워크 요청 전에 거부한다.
- 비공개 저장소 또는 접근할 수 없는 저장소는 지원 범위를 안내한다.
- 존재하지 않는 문서 폴더는 빈 목록과 구분되는 오류로 표시한다.
- GitHub API 요청 한도 초과 또는 네트워크 실패 시 재시도 가능한 오류를 표시한다.
- Markdown 파싱 실패는 애플리케이션 전체 오류로 확산되지 않아야 한다.

## 비기능 요구사항

### 실행성

- 신규 사용자는 프로젝트의 실행 안내에 따라 단일 명령으로 로컬 웹 애플리케이션을 시작할 수 있어야 한다.
- 별도 클라우드 계정이나 서버형 데이터베이스가 없어야 한다.

### 보안 최소선

- GitHub 토큰, OAuth 또는 사용자 계정 정보를 수집하거나 저장하지 않는다.
- GitHub 외 임의 호스트로 서버 측 요청을 보내지 않는다.
- 렌더링된 Markdown의 스크립트와 위험한 HTML을 제거한다.
- 입력값은 서버에서 검증하며 오류에 비밀정보나 내부 스택을 노출하지 않는다.

### 테스트 범위

- 자동 테스트는 핵심 경로 스모크 테스트로 제한한다.
- 스모크 테스트는 공개 저장소 문서 로드, 질문 추출, 답변 저장, 재조회 및 Markdown 내보내기를 검증한다.
- 성능, 부하, 고가용성, 복원력 및 속성 기반 테스트는 수행하지 않는다.

## MVP 제외 범위

- 테이블오더 기능
- GitHub 로그인, OAuth, 비공개 저장소 및 권한 동기화
- GitHub Enterprise Server 지원
- 원격 저장소 파일 수정, 커밋 또는 Pull Request 생성
- 다중 사용자, 그룹, 역할 및 승인 권한
- 문서 댓글, 영역별 토론 및 의견 요청 워크플로우
- LLM 기반 문서 요약 및 시각화
- 실시간 동기화 및 알림
- 외부 환경 배포
- 성능, 확장성, 고가용성 및 복원력 설계

## MVP 완료 기준

- 공개 GitHub 저장소와 문서 폴더를 지정해 Markdown 문서를 볼 수 있다.
- 기본 AI-DLC 질문 형식에서 미결정 사항을 추출해 대기열에 표시할 수 있다.
- 하나 이상의 답변을 선택하여 SQLite에 저장할 수 있다.
- 저장된 답변이 애플리케이션 재시작 후에도 유지된다.
- 답변이 반영된 Markdown을 내려받을 수 있다.
- 핵심 경로 스모크 테스트가 통과한다.

## 확장 규칙 결정

| 확장 규칙              | 적용 여부 | 근거                                      |
| ---------------------- | --------- | ----------------------------------------- |
| Security Baseline      | 비활성    | 1.5일 MVP이며 최소 보안 처리만 직접 요구  |
| Property-Based Testing | 비활성    | 스모크 테스트만 수행하도록 명시됨         |

## 전제

- 인터넷 연결을 사용할 수 있다.
- 대상 GitHub 저장소는 공개 상태이다.
- 기본 브랜치의 현재 문서를 조회한다.
- MVP는 한 번에 하나의 저장소를 대상으로 사용한다.
