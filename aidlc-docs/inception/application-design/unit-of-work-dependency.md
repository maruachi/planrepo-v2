# PlanRepo 단위 의존성

## 기준

[단위 정의](unit-of-work.md), [구성 요소 의존성](component-dependency.md), [서비스 흐름](services.md)을 따른다. `planrepo`는 전체 앱을 포함하는 단일 구현 단위다.

## 단위 간 의존성 행렬

행은 의존하는 단위, 열은 대상 단위다. `없음`은 다른 단위 호출 또는 자기 의존성이 없음을 의미한다.

| 단위 | planrepo |
| --- | --- |
| planrepo | 없음 |

다른 구현 단위가 없으므로 선행 단위의 산출물을 기다리거나 단위 간 API·공유 DB를 설계할 필요가 없다. GitHub는 외부 읽기 대상이고 SQLite는 로컬 저장소이며, 둘 다 별도 개발 단위가 아니다.

## 단위 내부 직접 호출

| 호출자 | 직접 호출 대상 | 통신과 책임 |
| --- | --- | --- |
| C1 ReviewUI | C2 PlanRepoService | 브라우저와 로컬 앱의 요청·응답. 연결·조회·확정·다운로드 |
| C2 PlanRepoService | C3 GitHubSource | 같은 프로세스 호출. 입력 정규화와 원문 집합 읽기 |
| C2 PlanRepoService | C4 QuestionParser | 같은 프로세스 호출. 원문의 질문과 경고 추출 |
| C2 PlanRepoService | C5 MarkdownRenderer | 같은 프로세스 호출. 안전한 HTML 생성 |
| C2 PlanRepoService | C6 DecisionStore | 같은 프로세스 호출. 최근 연결과 결정 조회·일괄 저장 |
| C2 PlanRepoService | C7 MarkdownExporter | 같은 프로세스 호출. 원문과 검증된 확정 결정으로 파일 생성 |

직접 호출은 C1 → C2 → C3~C7 순서이며 순환하지 않는다. 반환값이 호출자에게 돌아오는 것은 역방향 호출 의존성이 아니다. C4와 C7은 DB·네트워크를 사용하지 않으며 C7은 C4를 직접 호출하지 않는다. 공통 데이터 타입은 UI나 저장 구현에 의존하지 않는다.

## 외부·저장 경계

| 구성 요소 | 대상 | 방향·권한 | 실패 시 결과 |
| --- | --- | --- | --- |
| C3 GitHubSource | 공개 GitHub | 검증된 GitHub 호스트로 읽기만 수행, 토큰 없음 | 접근·폴더·네트워크·요청 한도 오류를 사용자에게 전달 |
| C6 DecisionStore | 로컬 SQLite 파일 | 최근 연결·확정 답변 조회와 트랜잭션 저장 | 저장 실패 응답, UI 임시 선택 유지 |

GitHub 이외 임의 호스트로 서버 측 요청을 보내지 않는다. 원격 쓰기 경계는 없다. C1은 GitHub·SQLite에 직접 접근하지 않고 C6만 SQLite를 소유한다. 구체적인 네트워크·DB 라이브러리와 호스트 검증 구현은 후속 NFR 단계에서 정의한다.

## 데이터 결합과 일관성

1. C3이 반환한 원문·버전 정보를 C2가 보유하고 같은 원문을 C4에 전달한다.
2. C2는 C6의 저장 결정을 현재 문서·질문에 연결 가능한지 검사하여 결합한다.
3. 대기열·문서 열람·내보내기는 같은 ReviewContext를 기준으로 한다. C5의 HTML은 표시 전용이다.
4. C2는 모든 확정 후보를 검증한 뒤 C6에 한 트랜잭션으로 저장한다. 저장되지 않은 선택을 완료로 표시하지 않는다.
5. C2는 현재 원문과 호환되는 확정 결정만 C7에 전달한다. C7은 답변 위치 이외 원문을 보존한다.
6. 재시작 후 최근 연결·결정은 C6에서 복원하고 GitHub 원문을 다시 읽어 새 컨텍스트에 연결한다.

원문 답변과 저장 답변의 우선순위, 질문 식별·변경 판정과 답변 위치 검증은 Functional Design의 책임이다. 이 단계에서 별도 동기화 서비스나 복원력 설계를 추가하지 않는다.

## 후속 설계 준비 조건

승인된 요구사항, 스토리와 상위 설계가 있으며 외부 선행 개발 단위는 없다. 단위 산출물 승인 후 `planrepo`의 Functional Design으로 진행할 수 있다. 실제 GitHub 접근과 SQLite 저장·복원 동작은 Build and Test의 핵심 경로 스모크 검증에서 확인한다. 현재 단계는 의존성 문서 검증만 수행했다.
